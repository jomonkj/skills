# The `yard` CLI: one handler core, two transports, zero AI

The skills (`/ship`, `to-issues`, `to-prd`, `triage`, `setup-*`) repeat the same `gh`/`git` plumbing — resolving scope, building dependency trees, ensuring labels, creating issues, dispatching worktrees, waiting on CI. Done as raw `gh` calls inside skill prompts this costs ~25 model round-trips per slice: every call is output tokens to emit plus a result blob that rides in context for the rest of the run and is re-read by the `/goal` evaluator every turn. It also lets label colours and formats drift across four skills.

We build one Bun TypeScript tool, `yard`, that the skills shell out to. Bun because the rest of yolo-hq already runs on it — Shell+jq or Python would add a runtime for no gain. The architecture is **one pure handler per operation, two thin transports over it**: a CLI entry (argv → handler → stdout JSON) and an MCP entry (`yard mcp`, stdio server → same handler). Zod schemas are the single source for CLI parsing, the MCP tool schema, and docs. Adding a subcommand is one handler plus one schema; both transports pick it up.

The CLI is primary and ships first: zero setup, works under `claude -p` headless, in cron, and on any machine. MCP is an optional layer for the hot `/ship` loop, where boundary schema-validation removes blind retry round-trips. We do not go MCP-only — portability and headless runs need the CLI. The bundling win (≈25 → ≈5 calls per slice) is identical for both transports; the MCP-vs-CLI difference is second-order noise.

**Hard rule: `yard` carries no AI.** Only `git`, `gh`, filesystem, JSON/YAML. It never spawns `claude`, no LLM call, no Agent. This keeps it fast, offline-runnable, and unit-testable with the gh/git layer mocked at zero token cost. All AI judgment lives in the skills that call it. The retired `review-sweep` (which made a structured Anthropic call) is therefore *not* folded into `yard`; it is dropped, its job absorbed by the layered review model (ADR 0004).

> **Update (2026-05-15):** the single-`.yard/config.yml` model implied here is superseded by the three-scope config + synced registry in ADR 0006. `.yard/config.yml` still exists but now carries only per-release-line data; project layout, protected lines, and the branch-delete guard move to the synced registry. `yard`'s surface also gains registry/profile commands (`init`, `project add/list/sync`, `doctor`).

`yard`'s surface is two-tiered: shared plumbing (`scope`, `deps`, `labels-ensure`, `issue-create`) used by many skills; ship-only (`dispatch-init`, `dispatch-done`, `ci-wait`, `sweep`) used only by `/ship`. As part of the big-bang (ADR 0002), `to-issues`, `to-prd`, `triage`, and the merged `setup-yard` are **migrated onto the shared plumbing in the same change** — not deferred. Leaving them on raw `gh` would keep four skills drifting on label colours/descriptions and issue formats, which defeats the single-source-of-truth purpose; full adoption now is the decision, not /ship-only. Operational invariants — idempotency, atomic single-call label moves, a lock so `/goal` re-entry can't double-dispatch, bounded `ci-wait`, partial-failure isolation across repos, deterministic sorted output, `--dry-run`, and cross-repo `Blocked by` resolution (parse both `owner/repo#N` and bare `#N`; resolve each blocker's state in its own repo) — are part of the contract, not optional.
